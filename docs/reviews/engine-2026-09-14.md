방식: 읽기 전용. `crates/nl-engine` 는 한 줄도 수정하지 않았다.

## 처리 현황 (2026-09-14 기준)

상태는 넷이다. **수정됨** = 고쳤고 회귀 시험이 있다. **부분** = 핵심은 고쳤으나 남은 한계를 따로 적었다.
**진행 중** = 담당자가 작업하고 있다. **미처리** = 아직 손대지 않았다.

**B1~B7 과 S1~S9 는 모두 처리했다** (2026-09-14, `agent/engine`). 뒤이어 "개선" 8건도 반영해 표가 24행이다.
근거 칸은 `파일:함수` 와 회귀 시험 이름이다.
보안 리뷰 쪽 현황표는 `docs/reviews/security-2026-09-14.md` 에 있다.

## 버그

### B1. Accuracy 지표가 단일 출력 모델에서 "라벨 0 비율"을 내놓는다

- 위치: `crates/nl-engine/src/train.rs:842-858`
- 왜 문제인가: `rows_cols` 가 출력 `[B,1]` 에서 `c=1` 을 준다. 원소 하나짜리 행의 `argmax` 는 항상 0 이므로 `pred` 가 언제나 0 이고, `hit` 은 "타깃이 0 인 샘플 수"가 된다. 즉 정답률이 아니라 라벨 0 의 기저 비율이다. `BceWithLogits` 로 이진 분류를 하는 가장 흔한 구성이 그대로 걸린다. 기본 `Metric` 이 `Accuracy` 라 사용자가 따로 켜지 않아도 노출된다.
- 재현: 출력 1 유닛 MLP + `Loss::BceWithLogits` + `Metric::Accuracy`, XOR 600 샘플, 40 에포크, `val_split=0.3`.
  관측: `train_loss=0.453222  val_loss=0.4567  val_metric=0.48333`.
  손실은 내려가는데 지표는 검증셋의 라벨 0 비율에 고정된다.
- 권장 수정: `c == 1` 이면 argmax 대신 임계값으로 예측을 만든다.

```rust
Metric::Accuracy => {
    let (b, c) = rows_cols(out)?;
    let tc = target.data.len() / b.max(1);
    let mut hit = 0usize;
    for i in 0..b {
        let (pred, truth) = if c == 1 {
            // 단일 로짓: 0 을 기준으로 이진 판정 (시그모이드 0.5 와 동치).
            ((out.data[i] >= 0.0) as usize, (target.data[i] >= 0.5) as usize)
        } else {
            let t = if tc == 1 { target.data[i] as usize }
                    else { argmax(&target.data[i * tc..(i + 1) * tc]) };
            (argmax(&out.data[i * c..(i + 1) * c]), t)
        };
        if pred == truth { hit += 1; }
    }
    Ok(hit as f64 / b as f64)
}
```

- 테스트 제안: `host_metric` 은 비공개이므로 통합 테스트로 잡는 편이 낫다. XOR 을 출력 1 유닛 + BCE 로 충분히 학습시키고 `run.epochs.last().val_metric > 0.9` 를 단언한다. 현재 코드로는 약 0.48 에 머무른다.

### B2. CrossEntropy 클래스 인덱스 범위 검사가 학습 경로에만 빠져 있다

- 위치: `crates/nl-engine/src/train.rs:730-733` (검사 없음) 대 `crates/nl-engine/src/train.rs:817-821` (검사 있음)
- 왜 문제인가: 검증용 `host_loss` 는 "클래스 인덱스 {k} 가 클래스 수 {c} 를 넘습니다"라고 정확히 알려주는데, 역전파가 걸리는 `device_loss` 는 검사 없이 `logp.gather(1, idx)` 를 부른다. ndarray 백엔드는 `tensor[[b, index.elem::<i64>() as usize]]` 로 그냥 인덱싱하므로(`burn-ndarray-0.21.0/src/ops/base.rs:126`) 패닉한다. wgpu 커널에는 그런 경계 검사가 아예 없어 조용히 엉뚱한 값을 읽을 수 있다. ImageFolder 의 클래스 폴더 수보다 출력 유닛이 적으면 바로 걸리는, 매우 흔한 사용자 실수다.
- 재현: `Quadrants`(라벨 0..3) 200 샘플에 출력 2 유닛 + `Loss::CrossEntropy` 로 학습.
  관측: `thread 'nl-train' panicked at ndarray-0.17.2/src/arraytraits.rs:36: ndarray: index out of bounds`
  → `[FAILED] 학습 스레드가 패닉했습니다: ndarray: index out of bounds`
  레이어 이름도, 문제의 인덱스도, 클래스 수도 나오지 않는다.
- 권장 수정: 두 가지 중 하나. (a) 데이터 적재 직후 `info.classes.len()` 과 첫 Output 폭을 대조해 미리 막는다. 가장 싸고 메시지가 가장 좋다. (b) 상주 경로라면 업로드 시 타깃 최댓값을 1회 계산해 검사한다. 배치마다 `into_scalar()` 를 부르는 것은 GPU 동기화 때문에 피한다.
- 테스트 제안: 위 재현 구성 그대로 `try_train` 계열 헬퍼로 돌려 오류 문자열에 "클래스" 가 포함되는지 단언한다.

### B3. Embedding 이 인덱스를 검사하지 않고 소수부를 조용히 버린다

- 위치: `crates/nl-engine/src/exec.rs:672-685`
- 왜 문제인가: `t.int()` 는 0 방향 절단이라 0.9 가 인덱스 0 이 된다(`burn-tensor-0.21.0/src/tensor/api/float.rs:142` → `float_into_int`). 정규화를 거친 실수 입력을 Embedding 에 물리면 대부분이 인덱스 0 으로 뭉개지는데 아무 경고가 없다. 범위를 넘으면 백엔드 깊은 곳에서 터진다.

  shape::infer 오류 수 = 0

### B6. Normalize 의 `std` 길이가 검증되지 않는다

- 위치: `crates/nl-engine/src/codec.rs:336-356` (특히 345행)
- 왜 문제인가: `mean.len()` 은 채널 수와 대조하는데 `std.len()` 은 아무 검사가 없다. `pick` 이 `v[i % v.len()]` 로 감싸므로 채널 3에 `std` 2개를 주면 세 번째 채널이 첫 번째 std 를 다시 쓴다. 정규화가 조용히 틀어지고 오류도 경고도 없다.
- 권장 수정: 한 줄이면 된다.

```rust
if mean.len() != 1 && mean.len() != channels {
    bail!("Normalize mean 길이 {} 가 채널 {} 과 맞지 않습니다", mean.len(), channels);
}
if std.len() != 1 && std.len() != channels {
    bail!("Normalize std 길이 {} 가 채널 {} 과 맞지 않습니다", std.len(), channels);
}
```

- 테스트 제안: `Image { channels: 3 }` 필드에 `Normalize { mean: vec![0.0;3], std: vec![1.0, 2.0] }` 를 걸고 `encode` 가 오류를 내는지 단언한다. 현재는 통과하며 3번 채널이 std 1.0 을 쓴다.

### B7. 조기 종료가 가장 좋은 가중치를 남기지 않는다

- 위치: `crates/nl-engine/src/train.rs:390-406` (early stop) 과 `crates/nl-engine/src/train.rs:409-413` (최종 저장)
- 왜 문제인가: `best_val` 은 patience 계산에만 쓰인다. 저장되는 것은 `final.safetensors` 하나뿐이고 `run.checkpoint` 도 그것을 가리킨다. 조기 종료는 정의상 "patience 에포크만큼 나빠진 뒤" 멈추므로, 남는 모델은 항상 최적점보다 열화된 쪽이다. 조기 종료를 켠 사용자가 얻고자 한 것과 정반대다. `checkpoint_every` 가 우연히 맞아떨어지지 않는 한 최적 가중치는 사라진다.
- 권장 수정: 검증 손실이 갱신될 때마다 `best.safetensors` 를 쓰고, 조기 종료로 끝났으면 `run.checkpoint` 를 그쪽으로 둔다. `RunRecord` 에 필드를 더하기 싫다면 최소한 `TrainEvent::Checkpoint` 로 경로를 알리고 로그에 "최적 에포크 N 의 가중치를 남겼습니다"를 남긴다.
- 테스트 제안: 일부러 과적합시켜 검증 손실이 오르게 한 뒤, 저장된 체크포인트로 `Session` 을 만들어 낸 검증 손실이 `run.best_val_loss()` 와 일치하는지 단언한다.

## 의심

### S1. BatchNorm running_var 가 편향 분산이다

`crates/nl-engine/src/exec.rs:754-760`. 정규화 자체에 편향 분산을 쓰는 것은 맞지만, PyTorch 는 running_var 갱신에만 불편 추정치(`n/(n-1)` 보정)를 쓴다. 평가 모드 출력이 PyTorch 와 미세하게 달라지고 배치가 작을수록 차이가 커진다. 의도한 단순화라면 `BatchNorm` 문서에 한 줄 적어 두는 편이 낫다. momentum 방향(`new = old*(1-m) + batch*m`)과 학습/평가 분기, running 통계를 `detach` 로 그래프에서 떼는 처리는 모두 올바르다.

한 가지 덧붙이면, `running_mean` 자체는 `detach` 되지 않은 채 `mul_scalar`/`try_add` 를 거친다(759-760행). 이 텐서는 `require_grad` 가 걸린 적이 없어 burn 이 노드를 만들지 않으므로 현재는 안전하지만, 백엔드 동작에 의존하는 부분이라 명시적으로 `.detach()` 를 붙여 두면 더 튼튼하다.

### S2. 그래디언트 노름이 비유한이면 클리핑이 조용히 꺼진다

`crates/nl-engine/src/train.rs:924-932`. `total.is_finite() && total > grad_clip` 조건 때문에 NaN/Inf 노름일 때 스케일링을 건너뛰고 원본 그래디언트가 그대로 파라미터에 들어간다. 클리핑이 존재하는 이유가 바로 그 경우다. 다음 스텝 손실 검사(343-345행)에서 `Failed` 로 끝나므로 잘못된 체크포인트가 남지는 않지만, 스텝을 통째로 건너뛰고 로그를 남기는 편이 낫다.

### S3. ImageFolder 클래스 인덱스가 문자열 정렬 순이다

`crates/nl-engine/src/data.rs:261-272`. `v.sort_by(|a, b| a.0.cmp(&b.0))` 는 바이트 순 정렬이라 폴더 이름이 `0`..`11` 이면 0,1,10,11,2,… 순이 된다. 폴더 이름이 곧 클래스 번호라고 믿는 사용자는 인덱스가 어긋난 채 학습하게 된다. `Recorded` 는 `labels.jsonl` 의 라벨 값을 그대로 쓰므로 두 소스의 의미가 다르다는 점도 문서에 적을 만하다. 자연 정렬을 넣거나, 최소한 `DatasetInfo.classes` 를 UI 에서 인덱스와 함께 보여 주도록 한다.

### S4. 체크포인트의 모델 id 를 로드할 때 확인하지 않는다

`crates/nl-engine/src/weights.rs:41-44` 가 메타데이터에 `model` 을 쓰지만 `weights::load` 도 `exec.rs:415-427` 의 `load_host_params` 도 읽지 않는다. 다른 모델의 체크포인트를 얹으면 `체크포인트에 파라미터 '{uuid}.weight' 이 없습니다` 라는 무의미한 메시지가 나온다. 메타데이터가 바로 그 용도로 있으므로, 다르면 "이 체크포인트는 다른 모델의 것입니다"로 바꾸는 것이 좋다. `format` 처럼 경고만 남기고 계속 읽는 정책도 가능하다.

### S5. 여분 파라미터가 조용히 무시된다

`crates/nl-engine/src/exec.rs:415-427` 은 모델 쪽 파라미터만 순회한다. 누락은 오류지만 파일에 남는 텐서는 아무 말 없이 버려진다. 레이어를 지운 뒤 옛 체크포인트를 얹으면 "성공"으로 보이므로, 남는 이름 개수를 세어 경고 로그를 남기는 편이 낫다.

### S6. MapLabel 도 단일 출력에서 항상 라벨 0 이다

`crates/nl-engine/src/codec.rs:380-391`. `data.len() == 1` 이면 `data[0] as usize` 로 확률 0.7 이 인덱스 0 으로 잘린다. B1 과 같은 형태의 결함이며, 단일 로짓 이진 분류기의 디코드 체인이 조용히 첫 라벨만 돌려준다. 범위 밖 인덱스 자체는 `labels.get(idx)` 가 제대로 잡는다. 단일 원소일 때는 `Threshold` 를 먼저 거치도록 문서화하거나, 라벨이 2개면 임계값 판정으로 처리한다.

### S7. probe 캐시의 check-then-insert 경쟁

`crates/nl-engine/src/device.rs:250-260`. 조회(254행)와 삽입(258행) 사이에 락이 풀린다. 두 스레드가 같은 키로 20초짜리 GPU 검사를 동시에 돌릴 수 있고, 먼저 끝난 결과는 덮어써진다. 맵은 `parking_lot::Mutex` 로 보호되니 자료구조 수준의 데이터 경쟁은 아니지만, 캐시의 목적(비싼 검사를 한 번만)이 무너지고 불안정한 드라이버를 두 번 두드린다. 키별 `OnceLock` 이나 in-flight 표식(`HashMap<ProbeKey, Arc<OnceLock<..>>>`)으로 고친다.

### S8. probe 타임아웃 시 스레드가 누수된다

`crates/nl-engine/src/device.rs:271-287`. `rx.recv_timeout` 이 만료되면 함수는 Err 를 돌려주지만 검사 스레드는 GPU 를 붙든 채 계속 돈다. 나중에 성공해도 이미 Err 가 캐시되어 결과가 버려진다. 주석에 "최악의 경우 응답하지 않는다"고 적혀 있으니 의도된 트레이드오프로 보이지만, 누수 사실 자체를 주석에 명시하는 편이 좋다.

### S9. `resolve(Auto)` 의 UI 스레드 위험이 절반만 문서화되어 있다

`crates/nl-engine/src/device.rs:350-362`. 첫 호출이 수십 초 걸릴 수 있다고는 적혀 있지만, `describe`(403행)처럼 "UI 스레드가 20 초 멈추면 안 되기 때문이다"라고 못박지는 않는다. `enumerate()`(208-212행)도 첫 호출에서 어댑터를 열거하므로 같은 성질이다. 두 함수 모두 "백그라운드에서 부를 것"을 명시하고, GUI 쪽에 `probe_cached` 처럼 논블로킹 대응물이 있는지 확인하는 것이 좋다.

## 개선

- **손실 구현이 둘로 갈라져 있다.** `device_loss`(`train.rs:695-739`)와 `host_loss`(`train.rs:790-830`)가 같은 손실 4종을 두 번 구현한다. 실제로 한쪽에만 경계 검사가 있어서 B2 가 생겼다. 검증도 장치에서 계산하거나, 한쪽을 다른 쪽으로 위임해 정의가 한 곳에만 있게 한다.
- **스텝마다 장치 동기화가 여러 번 일어난다.** `loss.clone().into_scalar()`(`train.rs:342`)가 스텝당 1회, 그래디언트 클리핑의 `g.sum_squares()`(`train.rs:925`)가 파라미터 수만큼 추가로 동기화를 건다. GPU 에서는 이 비용이 지배적일 수 있다. 발산 검사를 N 스텝마다 하거나, 노름을 텐서 연산으로 합쳐 한 번만 읽는다.
- **`TrainEvent::Step` 이 무한 채널로 스텝마다 나간다.** UI 가 늦게 비우면 메모리가 계속 는다. 배치가 많은 실행에서는 샘플링하거나 유계 채널을 고려한다.
- **CSV 열 오류가 사용자 입력 대신 해석된 번호를 보여 준다.** `crates/nl-engine/src/data.rs:233` 의 "CSV {row}행에 열 {i} 이 없습니다" 에서 `i` 는 0 기반 인덱스다. 이름으로 지정한 사용자는 자기가 쓴 문자열을 볼 수 없다. `resolve_col` 이 `(spec, idx)` 쌍을 들고 다니면 해결된다.
- **`Model::build` 의 오류 선택이 임의적이다.** `crates/nl-engine/src/exec.rs:349-353` 은 `report.errors.iter().next()` 로 BTreeMap 의 id 순 첫 노드를 고른다. 실제 원인과 무관한 떠 있는 노드가 지목될 수 있다. 오류를 전부 모아 보여 주거나, 출력에서 역방향으로 도달 가능한 노드를 우선한다.
- **`scan_source` 가 이미지 없는 폴더에서 빈 형상을 조용히 돌려준다.** `crates/nl-engine/src/data.rs:86-97`. 클래스 폴더는 있는데 이미지가 없으면 `input_shape: vec![]`, `samples: 0` 이 나온다. `load_image_folder` 는 같은 상황에서 오류를 내므로 두 경로가 어긋난다.
- **`preview` 의 limit 이 첫 클래스만 보여 준다.** `crates/nl-engine/src/data.rs:342-345`. 내부 루프에서만 break 하므로 개수는 맞지만 표본이 첫 클래스에 몰린다. 미리보기 용도로는 클래스별로 고르게 뽑는 편이 유용하다.
- **decode 의 방향성 비대칭을 문서화한다.** 아래 "확인한 정상 동작" 참고.

## 확인한 정상 동작

지시하신 점검 항목 중 문제가 없는 것도 적어 둔다.

- **Conv2d**: kaiming `fan_in` 이 커널 면적을 포함한다(`exec.rs:479`, `s[0] * kernel[0] * kernel[1]`). 패딩·스트라이드는 `ConvOptions::new(stride, padding, [1,1], 1)` 로 `conv_out` 규칙과 일치한다.
- **풀링**: `max_pool2d(.., [0,0], [1,1], false)` 와 `avg_pool2d(.., [0,0], true, false)` 의 `ceil_mode=false` 가 `conv_out` 의 floor 규칙과 맞는다(burn 0.21 시그니처 확인).
- **GlobalAvgPool**: `mean_dim` 이 차원을 유지한다는 것을 burn 문서에서 확인했다(`burn-tensor-0.21.0/src/tensor/api/numeric.rs:390` 및 `mean_dims` 주석 "the aggregated dimensions will have size 1"). `[B,C,H,W] → [B,C,1,1] → [B,C]` 로 올바르다.
- **Concat**: 배치 제외 인덱스에 `+1` 을 붙여(`exec.rs:670`) `shape::rule` 의 샘플 기준 `dim` 과 정확히 맞는다.
- **Reshape / Flatten**: 원소 수 검사가 `shape::rule` 과 `DynTensor::reshape` 양쪽에 있다. (랭크 상한만 B5 로 빠져 있다.)
- **LayerNorm**: 마지막 차원 기준, `gamma`/`beta` 를 `[1,..,n]` 으로 브로드캐스트, `sqrt(var + eps)` 형태 모두 표준이다.
- **BatchNorm**: 학습/평가 분기, running 통계 갱신 시점, momentum 방향이 PyTorch 규약과 같다. (편향 분산만 S1.)
- **Dropout**: 역스케일링 `1/keep` 이 올바르고, `!train || p <= 0.0` 이면 항등, `p >= 1.0` 은 오류다. `1.0 - *p as f64` 의 연산자 우선순위도 의도대로다.
- **옵티마이저**: SGD momentum 버퍼(`buf = m*momentum + g`, `p -= lr*buf`), Adam 편향 보정(`1 - beta^t`, `t` 는 스텝 전역 카운터), eps 위치(`m_hat / (sqrt(v_hat) + eps)`), AdamW 의 decoupled decay 가 그래디언트가 아니라 파라미터에 적용되는 것(`train.rs:1005`, `p *= 1 - lr*wd`) 모두 올바르다.
- **LR 스케줄**: Step 은 `gamma^((epoch-1)/every)`, Cosine 은 마지막 에포크에서 정확히 `min_lr`, Plateau 는 에포크 시작에 읽고 에포크 끝에 갱신해 다음 에포크부터 반영, warmup 은 `(global_step+1)/warmup_steps` 라 첫 스텝 lr 이 0 이 되지 않는다. 경계값은 기존 단위 테스트가 이미 고정하고 있다.
- **BCE with logits**: `max(x,0) - x*z + log1p(exp(-|x|))` 로 수치적으로 안정한 형태다. 장치판과 호스트판의 평균 정의(원소 전체 평균)도 일치한다.
- **손실 평균 정의 일치**: MSE/MAE/BCE 는 `B*C` 평균, CrossEntropy 는 `B` 평균으로 장치판과 호스트판이 같다.
- **검증 분할과 재현성**: `train_set.shuffle` 이 먼저(`train.rs:272`), `split_off` 가 나중(`train.rs:285`)이라 검증셋이 셔플된 표본에서 나온다. 시드는 초기 셔플 `cfg.seed`, 에포크별 `cfg.seed + epoch`, 파라미터 초기화 `B::seed(device, cfg.seed)` 로 모두 결정적이다.
- **상주 배치 경로**: `permuted` 와 `batch` 양쪽에 `detach` 가 걸려 있고(`train.rs:513-514`, `525-526`), 기존 테스트 `device_set_batches_match_host_stacking` 이 호스트 경로와의 동등성을 순열 포함해 검증한다.
- **`catch_unwind` 후 채널 정리**: `tx` 는 스레드 클로저가 소유하며 Finished/Failed 를 보낸 뒤 드롭되므로 수신자가 끊김을 본다. 릴리스 프로파일에 `panic = "abort"` 가 없어 `catch_unwind` 가 실제로 동작한다(재현 실험에서 확인).
- **pause/stop 경로의 체크포인트**: `break 'epochs` 이후에도 `final.safetensors` 를 쓰고 `run.status` 를 `Stopped` 로 둔다(`train.rs:409-414`). 조기 종료는 `Finished` 로 남는다.
- **추론**: `infer.rs:147` 이 `forward(tensors, false)` 를 부르므로 Dropout 은 항등, BatchNorm 은 running 통계를 쓴다. 다입력 순서는 학습과 추론 모두 `Graph::input_nodes()`(이름 → id 정렬)를 따르고 `Session::input_sample_shapes()` 로 같은 순서를 노출한다.
- **safetensors**: 이름·형상 검증, f32 강제, 4바이트 정렬 검사, 원자적 저장(tmp + rename)이 모두 있다. 누락 파라미터는 오류다. (여분은 S5, 모델 id 는 S4.)
- **codec 의 encode 범위 검사**: `ClassLabel`(`codec.rs:137`), `OneHot` encode(`codec.rs:289`), `OneHot` decode(`codec.rs:406`), `MapLabel`(`codec.rs:387`) 모두 범위를 확인한다.
- **이미지 리사이즈·정규화 순서**: `data.rs:305-325` 는 u8 이미지에서 `resize_exact` 를 먼저 하고 그다음 `/255.0` 을 적용한다. 올바른 순서다. 체인 중간의 `Transform::Resize` 가 f32 평면에서 이중선형 보간을 쓰는 이유도 주석에 정확히 적혀 있다(`codec.rs:436-439`).
- **decode 체인의 방향**: 질문하신 "decode 역순 여부"의 답은 "역순이 아니다"이며, 이는 설계대로다. `field.decode` 는 `field.encode` 의 역순 자동 적용이 아니라 독립적인 정방향 목록이고, `payload.rs` 의 계약(`encode: 바깥 → 텐서`, `decode: 텐서 → 바깥`)과 일치한다. 다만 같은 `Transform` 변형이 decode 에서 의미가 갈린다. `Scale`·`Normalize`·`OneHot` 은 역변환이고 `Softmax`·`Argmax`·`Threshold`·`MapLabel` 은 정방향이다. 이 비대칭은 `payload.rs` 의 `Transform` 문서에 한 줄 적어 두는 편이 좋다.

## 실제 버그로 확신하는 것

| 번호 | 요약 | 확인 방법 |
|---|---|---|
| B1 | Accuracy 가 단일 출력에서 라벨 0 비율 | 재현 완료 (val_metric 0.483) |
| B2 | CrossEntropy 인덱스 범위 검사가 학습 경로에만 없음 | 재현 완료 (ndarray 패닉) |
| B3 | Embedding 인덱스 미검사 + 조용한 절단 | 재현 완료 (index < dim 패닉) |
| B4 | 출력 1개 + CrossEntropy 는 손실이 항상 0 | 재현 완료 (train_loss 0.000000) |
| B5 | 랭크 6 이상이 검증 통과 후 학습에서만 실패 | 재현 완료 (validate 문제 0개) |
| B6 | Normalize 의 std 길이 미검증 | 코드로 명백 |
| B7 | 조기 종료가 최적 가중치를 남기지 않음 | 코드로 명백 |

우선순위는 **B4 → B1 → B7 → B2 → B3 → B5 → B6** 순으로 본다. 앞의 셋은 실패가 조용해서 사용자가 잘못된 결론을 내린다. B4 는 학습이 무효인데 성공으로 보이고, B1 은 지표가 거짓이며, B7 은 조기 종료의 결과물이 의도와 반대다. B2 와 B3 은 실패하기는 하되 메시지가 원인을 전혀 알려주지 않는다. B5 는 편집기와 런타임의 계약 불일치이고, B6 은 한 줄 수정이다.
