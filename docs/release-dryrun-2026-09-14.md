## 사전 조건 (§1~§4)

### §1 서명 키 — 도구는 동작한다, 키는 없다

```sh
cargo run -p nl-update --example nl-keygen -- keygen --out <임시> --name dryrun
```

비밀키와 공개키가 나왔고 권한이 문서가 적은 대로였다.

| 파일 | 권한 | 크기 |
| --- | --- | --- |
| `<이름>.key` | 0600 | 294~297 B |
| `<이름>.pub` | 0644 | 114 B |

도구가 끝에 `gh secret set MINISIGN_KEY < <키파일>` 을 그대로 찍어 준다. 문서와 도구 출력이
같은 명령을 말한다.

`packaging/keys/` 에는 `README.md` 만 있다. `.gitignore` 12행이 `packaging/keys/*.key` 를 막는다 —
문서가 "비밀키는 `.gitignore` 가 막는다" 고 한 것이 사실이다. **드라이런은 진짜 키를 만들지 않았다.**
`packaging/keys/` 에 키를 두는 것은 사람이 한 번만 하는 일이고, 임시로 만들어 두면 진짜 키로
오해될 수 있어서다. 2부의 드라이런 키도 저장소 바깥 임시 폴더에만 두었다.

### §2 빌더 공개키 — 비어 있다

`crates/nl-app/src/update_key.rs` 의 `PUBLIC_KEY` 가 `None` 이다. 따라서 `ENABLED` 가 `false` 이고
빌더는 업데이트를 **확인조차 하지 않는다.** 주석이 이유를 적어 두었다 — 검증할 수 없으면 아예 묻지
않는 쪽이 안전하다. 지금 릴리스를 내면 자동 업데이트가 꺼진 채로 나간다.

2부에서 이 말이 사실인지 실제로 봤다 — ⑩ 에 있다.

### §3 CI 러너 — 문서에 없던 항목이었다 (추가함)

워크플로는 `runs-on: ubuntu-latest` 하나로 Linux 네이티브와 Windows 크로스를 함께 만든다.
GitHub 사본과 Forgejo 사본은 **바이트 단위로 같다**(`diff -q` 로 확인, 2부에서 다시 확인).
러너 전제 조건이 체크리스트에 없어서 절을 새로 넣었다. "찾은 문제 3" 참고.

### §4 배포 서버 — 주소는 살아 있으나 내용이 없다

```sh
curl -sSfI https://updates.trustanc.dev/neural-linker/latest.json
```

두 패스를 비교하다 알게 된 것 둘을 적어 둔다(고치지 않았다).

- **아카이브는 재현 가능하지 않다.** 같은 실행 파일을 두 번 포장했는데 `tar.gz` 의 크기와 해시가
  달랐고(62,773,234 → 62,773,001) `setup.exe` 도 크기는 같은데 해시가 달랐다. gzip 과 Inno Setup 이

  "같은 빌드인가" 를 판단할 수 있는 것은 실행 파일뿐이고 아카이브로는 안 된다.**
- `--installer` 는 `dist-local/neural-linker-installer/` 에 스테이징 사본(65 MB)을 남긴다. 설치
  프로그램이 없을 때 `.iss` 와 스테이징만 남기고 성공하는 설계라서 그런데, 성공했을 때도 남아
  산출물 표에 섞인다. CI 는 `--installer` 를 쓰지 않으므로 로컬에만 있는 군더더기다.

### ⑤ 태그

**수행하지 않았다** — 되돌리기 어렵고 바깥으로 나간다. 명령만 적는다.

```sh
git tag -a v0.2.0 -m "v0.2.0" && git push origin v0.2.0
```

대신 **버전이 어디서 오는지**를 확인했다. CI 의 "버전 확인" 단계와 로컬 스크립트가 같은 함수
(`packaging/lib.sh` 의 `nl_release_version`)를 쓴다.

| 입력 | 결과 |
| --- | --- |
| `refs/tags/v0.2.0` | `0.2.0` (태그에서) |
| 빈 `GITHUB_REF` (`workflow_dispatch`) | `0.1.0` (워크스페이스 `Cargo.toml` 에서) |

태그 없이 시험만 하려면 Actions 에서 `workflow_dispatch` 로 돌린다 — 빌드와 서명은 하고
릴리스 첨부만 건너뛴다.

### ⑥ CI 산출물 확인

CI 를 돌리지 않았으므로(러너가 아직 없다) **릴리스 자산이 만들어지는 자리를 로컬에서 재현**했다.
워크플로의 `릴리스 자산 이름 정리` 단계와 `files:` 목록을 그대로 흉내 내, ④ 의 산출물을 평평한
폴더에 이름만으로 복사해 보았다.

```sh
cp dist-local/runtimes/latest.json dist-local/runtimes-latest.json          # 워크플로가 하는 일
cp dist-local/runtimes/latest.json.minisig dist-local/runtimes-latest.json.minisig
```

| 결과 | 값 |
| --- | --- |
| 첨부 대상 | 10개 |
| 이름 충돌 | **0건** |
| `latest.json` 의 대상 | `linux-x86_64` (빌더 알맹이) |
| `runtimes-latest.json` 의 대상 | `linux-x86_64`, `windows-x86_64` (런타임) |

이름을 바꾸지 않으면 둘 다 `latest.json` 이 되어 하나가 다른 하나를 덮어쓴다 — 1부에서 고친
자리이고("찾은 문제 1"), 이번에 그 수정이 실제로 먹는 것을 확인했다.

첨부 목록에 `nl`·`nl.exe` 는 없다. 릴리스 자산 낱개는 **자동 업데이트가 내려받는 것**만 두는 것이
맞고, CLI 는 업데이터가 받아 오지 않는다. 사람이 받는 경로는 아카이브다 — 그래서 아카이브에는
들어가야 하고, 그것이 "찾은 문제 6" 이다.

### ⑦ 서명 검증

④ 둘째 패스의 매니페스트를 배포 앱과 같은 코드로 검증했다.

```sh
cargo run -p nl-update --example nl-keygen -- verify dist-local/latest.json --pubkey <드라이런 공개키>
cargo run -p nl-update --example nl-keygen -- verify dist-local/runtimes/latest.json --pubkey <드라이런 공개키>
```

둘 다 `서명이 맞습니다`. 매니페스트 안도 눈으로 봤다.

| 볼 것 | `latest.json` | `runtimes/latest.json` |
| --- | --- | --- |
| `version` 이 올린 버전과 같은가 | `0.1.0` ✔ | `0.1.0` ✔ |
| `published_at` 이 지금인가 (30일 지나면 앱이 거절) | `2026-09-15T01:01:55Z` ✔ | `2026-09-15T01:01:57Z` ✔ |
| 자산 `url` 이 https 이고 매니페스트와 같은 오리진인가 | ✔ | ✔ |
| 자산마다 `sha256` 과 `size` 가 있는가 | ✔ (1개) | ✔ (2개) |
| `sha256` 이 실제 파일과 맞는가 | ✔ | ✔ |

마지막 줄은 산출물 표의 해시와 매니페스트 안의 해시를 직접 맞춰 본 것이다.

### ⑧ 배포 서버 업로드

**실제 서버에는 올리지 않았다** — 바깥으로 나가고, 아직 503 이다(§4).

대신 **같은 배치를 루프백 서버로 만들어 올리는 연습**을 했다. 문서가 적은 폴더 모양 그대로다.

```
<base>/latest.json                      <base>/latest.json.minisig
<base>/runtimes/latest.json             <base>/runtimes/latest.json.minisig
<base>/0.2.0/nl-app
<base>/0.2.0/runtimes/nl-runtime        <base>/0.2.0/runtimes/nl-runtime.exe
```

올린 뒤 확인하라는 명령이 그대로 통했다.

```sh
curl -sSfI <base>/latest.json          # 200
curl -sSfI <base>/latest.json.minisig  # 200
curl -sSf  <base>/0.2.0/nl-app         # 200, 91,234,576 바이트
```

여기서 **매니페스트 도구가 루프백 주소를 거부해 이 연습을 아예 할 수 없었다**는 것을 알았다 —
받는 쪽에는 시험용 탈출구가 있는데 만드는 쪽에는 없었다. "찾은 문제 7" 이고, 고친 뒤에 위 배치를
만들 수 있었다.

### ⑨ 빌더에서 업데이트 확인

**처음으로 실제로 돌렸다.** 지금까지 이 경로는 `crates/nl-update/tests/server.rs` 의 통합 시험
22건으로만 확인돼 있었고, 빌더를 띄워 끝까지 가 본 적은 없었다.

차린 것:

- ⑧ 의 루프백 서버가 `0.2.0` 을 광고한다(⑦ 과 같은 드라이런 키로 서명).
- `update_key.rs` 의 `PUBLIC_KEY` 에 그 공개키를 **임시로** 넣고 `nl-app` 을 다시 빌드했다.
  릴리스 전에 사람이 할 일(§2)을 미리 해 본 것이다. 기록을 남긴 뒤 원래대로(`None`) 돌려놓았다.
- 헤드리스 sway 하네스(`tools/uitest`)에서 띄우고 `NL_UPDATE_URL`·`NL_ALLOW_HTTP=1` 을 줬다.

일어난 일:

| 순서 | 확인한 것 |
| --- | --- |
| 1 | 앱이 뜨자마자 서버에 `GET /latest.json`, `GET /latest.json.minisig` — 서명까지 받아 간다 |
| 2 | 툴바 오른쪽에 초록 배지 **`⬆ v0.2.0`**, 상태 표시줄은 `v0.1.0` |
| 3 | 배지를 누르면 "빌더 업데이트" 창 — `현재 v0.1.0` / `새 버전 v0.2.0 사용 가능` / 메모 `0.2.0 릴리스` |
| 4 | `⬇ 내려받기` → `GET /0.2.0/nl-app`, `자산을 받았습니다 … (91,234,576 바이트)` |
| 5 | `⬆ 적용하고 다시 시작` → 실행 파일이 **매니페스트가 말한 sha256 으로 바뀌었다** |
| 6 | 새 프로세스가 떴다 |

5번은 적용 전 `b76e458c…` 였던 `target/release/nl-app` 이 적용 뒤 `b39679e0…` 가 된 것으로 확인했다 —
매니페스트 자산의 sha256 과 정확히 같다.

여기서 **적용한 뒤 옛 빌더가 끝나지 않는다**는 것을 알았다. 새 프로세스와 옛 프로세스가 함께
남아 창이 둘이 됐다. "찾은 문제 8" 이고, 고친 뒤 같은 경로를 다시 돌려 **새 프로세스 하나만**
남는 것을 확인했다.

수행하지 못한 것 하나: **다시 뜬 앱의 `--version` 이 새 버전인지**는 보지 못했다. 서버에 올린
자산이 `0.1.0` 바이너리를 `0.2.0` 으로 광고한 것이라, 적용해도 `--version` 은 `0.1.0` 을 낸다.
이것을 보려면 실제로 버전을 올려 빌드한 자산이 필요하다 — 진짜 릴리스 때 자연히 확인된다.

공개키를 비운 빌드는 ⑨ 의 마지막에 저절로 확인됐다. 서버가 광고한 `0.2.0` 자산이 공개키를 넣기
전에 만든 실행 파일이었기 때문에, 적용하고 다시 뜬 앱이 곧 `PUBLIC_KEY = None` 빌드였다. 그 앱은

- 툴바에 배지가 없고,
- 서버에 **요청을 하나도 보내지 않았다** (서버 접근 기록이 더 늘지 않았다).

§2 가 말한 "확인조차 하지 않는다" 가 사실이다. `자원` 탭의 업데이트 자리는 "서명 키 미설정 —
업데이트 비활성" 과 그 이유를 알리고 조작 UI 를 감춘다.

Windows 실기 설치는 **수행하지 않았다.** 이 기계에는 Windows 가 없고, wine 에서의 설치는
1부 이전에 이미 한 번 확인한 항목이다(CHANGELOG "확인한 것"). 실기 검증은 사람이 남긴 일로 둔다.

또 하나: **Inno Setup 이 wine 접두사에서 사라져 있었다.** 내려받은 설치본
(`~/.cache/neural-linker/tools/innosetup-6.7.3.exe`)만 남고 접두사에는 `ISCC.exe` 가 없었다.
`nl_bundle::tools::install_inno_setup_plan` 이 적어 둔 대로 `wine … /VERYSILENT` 로 다시 깔았다.
**설치 프로그램을 만드는 단계는 이 도구가 있어야만 돈다** — 없으면 `.iss` 와 스테이징만 남기고
경고 뒤 zip 으로 간다.

## 찾은 문제

### 1부 (2026-09-14) — 커밋 `d15d7f9`

이 절은 1부 기록에서 유실됐다. 커밋 `d15d7f9` 의 변경 내용에서 복원한 것이다.

**1. 릴리스 자산 이름이 부딪혔다.** GitHub·Forgejo 릴리스 자산은 평평해서 이름이 basename
하나뿐이다. `dist/latest.json` 과 `dist/runtimes/latest.json` 을 그대로 붙이면 둘 다 `latest.json`
이 되어 하나가 다른 하나를 덮어쓴다. 릴리스만 보고는 어느 쪽이 올라간 것인지 알 수 없다.
→ 워크플로에 `릴리스 자산 이름 정리` 단계를 넣어 **릴리스에 붙일 사본만** `runtimes-latest.json`
으로 바꾼다. 폴더 구조가 살아 있는 것은 `산출물 보관` 아티팩트이고, 배포 서버에는 그쪽을 올린다.
2부 ⑥ 에서 이 수정이 먹는 것을 확인했다.

**2. 버전을 올린 뒤 확인하는 자리가 없었다.** 매니페스트의 `version` 은 태그에서 오고 바이너리의
`--version` 은 `Cargo.toml` 에서 온다. 둘이 어긋나면 사용자가 업데이트를 받고도 같은 버전을 계속
본다. → ① 에 `grep -m1 '^version' Cargo.toml` 과 `nl --version` 으로 확인하는 단계를 넣었다.

**3. 사전 조건에 CI 러너 항목이 없었다.** Forgejo 는 등록된 러너가 없으면 태그를 밀어도 잡이
큐에만 쌓이고 **실패로 보이지도 않는다.** 시크릿·변수도 GitHub 과 Forgejo 에 각각 넣어야 하는데,
한쪽에만 넣고 다른 쪽에서 태그를 밀면 서명 없는 릴리스가 나간다. → §3 절을 새로 넣었다.

**4. 서명 검증 명령의 경로 기준이 모호했다.** `verify latest.json` 이라고만 적혀 있어 어느 폴더에서
부르는 것인지 알 수 없었다. → `산출물 보관` 아티팩트를 푼 폴더를 `dist/` 라 못박고 `dist/latest.json`
으로 고쳤다.

**5. 배포 서버에 올릴 원본이 무엇인지 적혀 있지 않았다.** 릴리스 자산 낱개를 올리면 `runtimes/`
구조가 없어 런타임 매니페스트 경로가 깨진다. → ⑧ 에 "올릴 원본은 `산출물 보관` 아티팩트(`dist/`
통째)" 라고 적었다.

### 2부 (2026-09-15)

**6. CI 릴리스 아카이브에 명령줄 도구 `nl` 이 빠져 있었다.** 워크플로가 `-p nl-app -p nl-runtime`
만 빌드하고 포장하므로 `nl` 이 들어가지 않는다. 그런데 `packaging/linux/install.sh` 는 아카이브에
`nl` 이 있으면 `~/.local/bin` 에 설치하게 되어 있고, `docs/GUIDE.md` 는 설치 절 다음에 `nl` 을
바로 쓰는 명령으로 한 장을 통째로 안내한다. 문서대로 받은 사람에게는 `nl` 이 없다.
`packaging/release-local.sh` 는 기본값이 `nl-app,nl-runtime,nl-cli` 라 로컬 드라이런에서는 보이지
않았다 — **드라이런과 CI 의 기본값이 달라서 가려져 있던 자리다.**
→ 워크플로 두 사본에 `-p nl-cli` 를 넣고 아카이브에 `nl`·`nl.exe` 를 포함시켰다. 릴리스 자산
낱개에는 넣지 않는다(업데이터가 받아 오는 것이 아니다). `GUIDE.md` 의 설치 절에도 `nl` 을 적었다.

**7. 매니페스트를 만드는 도구가 루프백 http 를 거부해 ⑨ 를 연습할 수 없었다.** 받는 쪽
(`nl_update::url::require_https`)에는 "`NL_ALLOW_HTTP=1` 이고 호스트가 루프백일 때만" 이라는
시험용 탈출구가 있는데, 만드는 쪽(`packaging/make-manifest.sh`·`make-runtimes-manifest.py`)은
https 가 아니면 무조건 거절했다. 그래서 **클라이언트가 받아 주는 매니페스트를 이 저장소의 도구로는
만들 수 없었고**, `RELEASE.md` ⑨ 가 적어 둔 루프백 시험 자체가 불가능했다.
→ 두 도구에 받는 쪽과 **같은 두 조건**의 탈출구를 넣었다. 기본은 그대로 https 만 받고, 바깥 주소는
`NL_ALLOW_HTTP=1` 이 있어도 거절한다(`http://example.com` 거절, `http://127.0.0.1`·`http://[::1]`
허용, `https://` 는 종전대로).

**8. 업데이트를 적용해도 옛 빌더가 끝나지 않았다.** `nl_update::apply` 는 "어느 결과든 호출자가
앱을 끝내야 한다" 고 계약을 적어 두는데, `nl-app` 의 `tick_updater` 는 `Event::Applied` 에서 로그
한 줄만 남기고 아무것도 하지 않았다. 새 프로세스는 이미 떠 있으므로 **빌더가 둘 남는다** —
드라이런에서 pid 두 개를 확인했다.
→ `Applied` 를 받으면 `ViewportCommand::Close` 를 보낸다. 적용은 저장하지 않은 변경이 없을 때만
시작하므로 종료 확인은 다시 묻지 않는다. 고친 뒤 같은 경로를 다시 돌려 새 프로세스 하나만 남는
것을 확인했다.

**9. 검증 러너가 낡은 빌더를 시험하고 있었다.** `scripts/verify-all.sh` 의 "릴리스 빌드" 단계는
`nl-runtime` 과 `nl-cli` 만 만들고 `nl-app` 은 만들지 않았다. 그런데 `--gui` 시나리오는
`target/release/nl-app` 을 쓰고, 하네스(`tools/uitest/uitest.sh`)는 **그 파일이 없을 때만** 빌드한다.
낡은 바이너리가 남아 있으면 방금 고친 코드가 아니라 옛것을 시험하고도 **통과로 보고한다.**
이번에 실제로 그랬다 — 8 을 고친 직후 검증을 돌렸는데, ⑨ 의 업데이트가 `target/release/nl-app` 을
갈아치워 둔 상태여서 GUI 시나리오가 고치기 전 바이너리를 시험했다.
→ "릴리스 빌드" 단계에 `-p nl-app` 을 넣었다.

## 남은 것

체크리스트에서 **로컬로는 할 수 없어 비워 둔 칸**이다. 진짜 릴리스 때 채워진다.

| 단계 | 왜 못 했나 |
| --- | --- |
| ⑤ 태그 | 되돌리기 어렵고 바깥으로 나간다 |
| ⑥ CI 산출물 | 러너가 아직 없다 (§3). 자산이 만들어지는 자리는 로컬에서 재현했다 |
| ⑧ 실제 업로드 | 배포 서버가 503 이다 (§4). 배치와 확인 명령은 루프백으로 연습했다 |
| ⑨ 적용 뒤 `--version` | 자산이 `0.1.0` 바이너리를 `0.2.0` 으로 광고한 것이라 버전이 그대로다 |
| ⑩ Windows 실기 설치 | 이 기계에 Windows 가 없다 |
