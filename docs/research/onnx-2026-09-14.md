# ONNX 상호운용 실현 방안

조사일 2026-09-14 · 엔진 담당 · **코드 변경 없음(조사만)**
대상: 로드맵 M3 "ONNX 가져오기(추론 전용) / 내보내기(검토)"

---

## 요약 — 권고 세 줄

1. **내보내기와 가져오기는 완전히 다른 일이다.** 가져오기는 `tract-onnx` 하나로 끝나지만, **tract 는 ONNX 를 쓰지 못한다**
   (NNEF 만 저장한다). 내보내기는 우리가 protobuf `ModelProto` 를 직접 조립해야 한다.
2. **먼저 내보내기를 한다.** 우리 20종에서 `Input`·`Output`·`Dropout` 을 뺀 17종이 매핑 대상이고 그중 **14종은 변환 없이
   그대로 대응**한다. 진짜 일은 LSTM·GRU·어텐션 셋뿐이다. `tract` 를 **dev-dependency 로만** 넣어 왕복 검증하면
   **배포 바이너리는 1 바이트도 늘지 않는다**. 가져오기는 바이너리가 **34 MiB** 늘어나므로(+46%) 값어치를 따로 따져야 한다.
3. **opset 17 을 겨냥한다.** `LayerNormalization` 이 17 에서 들어왔고 tract 의 보장 범위가 9~18 이라, 17 이 둘을 모두 만족하는
   유일하게 넓은 지점이다.

첫 구현 조각은 **MLP/CNN 내보내기 + tract 재검증**이 맞다. 이유는 §3.2 에 적었다.

### tract 가 할 수 있는 것과 없는 것

| 포맷 | 읽기 | 쓰기 |
|---|---|---|
| ONNX | 가능 | **불가능** |
| NNEF (+ tract-OPL) | 가능 | 가능 |
| TensorFlow Lite | 가능 | 가능 |

출처: https://github.com/sonos/tract/blob/main/README.md 의 포맷 표. v0.23.7 소스에도 그래프→ONNX 익스포터가 없다.

**그러나 우회로가 있다.** `tract_onnx::pb` 모듈이 `ModelProto`·`GraphProto`·`NodeProto`·`TensorProto` 를 전부 `pub` 으로
내보내고 이들이 `prost::Message` 를 derive 한다. 즉 `ModelProto` 를 손으로 조립해 `.encode()` 하면 `.onnx` 파일이 나온다.
tract 자신의 테스트가 그렇게 한다(`onnx/src/ops/nn/simplified_layer_norm.rs`). 다만 tract README 가 내부 크레이트를
"not stable surface" 로 못박았으므로 이 경로에 기대는 것은 §3.3 에서 다시 따진다.

### tract 의 opset 지원 범위 — 9 ~ 18

`onnx/src/model.rs` 가 `!(9..19).contains(version)` 이면 경고를 찍는다. 하드 에러는 아니지만 **보장 범위 밖**이다.
이 한 줄이 우리 내보내기 opset 을 사실상 결정한다.

### tract 는 순수 Rust 인가

**런타임 외부 라이브러리 의존은 0 이다.** `libonnxruntime` 도 protobuf 런타임도 BLAS 도 링크하지 않는다. `protoc` 도 필요
없다 — 생성된 protobuf 코드가 `src/prost/onnx.rs` 로 커밋되어 배포된다(`onnx/Cargo.toml` 에 `build = false`).

**단 빌드 시 어셈블러가 필요하다.** `tract-linalg` 의 `build.rs` 가 `cc` 크레이트로 아키텍처별 어셈블리(x86_64 는 `.S`/
MSVC 는 `.asm`)를 컴파일한다. 리눅스 네이티브 빌드는 문제없고, Windows 크로스 빌드도 실측 결과 그대로 된다(§2.5).

## 1. 내보내기 — 연산자 매핑

### 1.1 목표 opset: **17**

| 제약 | 요구 opset |
|---|---|
| `LayerNormalization` 도입 | ≥ 17 |
| `Softmax`/`LogSoftmax` 가 축을 실제 축으로 해석 (16 이하는 2D 로 강제 변환) | ≥ 13 |
| LSTM/GRU 의 `layout` 속성 | ≥ 14 |
| `BatchNormalization` 의 `training_mode` 속성 | ≥ 14 |
| tract 보장 상한 | ≤ 18 |

→ **17 또는 18. 17 로 고정한다** (18 은 얻는 게 없다).

여기서 잘려 나가는 것이 둘 있다.

- **`Gelu` 는 opset 20 이라 쓸 수 없다.** `Erf` 로 전개한다(§1.3).
- **표준 `Attention` 은 opset 23 이라 쓸 수 없다.** 어텐션은 분해한다(§1.4). `com.microsoft.MultiHeadAttention` 은
  ONNX Runtime 전용 도메인이라 이식성이 없어 애초에 후보가 아니다.

### 1.2 `LayerKind` 20종 매핑

우리 그래프는 배치 차원을 형상에 담지 않는다(`Shape` 의 `Dim::Batch`). ONNX 로는 배치를 **심볼 `"B"`** 로 내보낸다 —
tract 가 `dim_param` 을 같은 이름의 심볼로 읽어 동적 배치가 그대로 산다.

| # | `LayerKind` | ONNX 연산자 | 난이도 | 비고 |
|---|---|---|---|---|
| 1 | `Input { shape }` | (그래프 입력 `ValueInfoProto`) | 쉬움 | `[B, ...shape]`, elem_type FLOAT. `Embedding` 앞이면 INT64 |
| 2 | `Output` | (그래프 출력) | 쉬움 | 항등이라 노드를 만들지 않는다 |
| 3 | `Linear { out_features, bias }` | `MatMul` (+ `Add`) | 쉬움 | **가중치 변환 불필요**(§1.3) |
| 4 | `Conv2d { .. }` | `Conv` | 쉬움 | **가중치 변환 불필요** |
| 5 | `MaxPool2d` | `MaxPool` | 쉬움 | `ceil_mode=0` |
| 6 | `AvgPool2d` | `AveragePool` | 쉬움 | 패딩을 안 쓰므로 `count_include_pad` 무관 |
| 7 | `GlobalAvgPool` | `GlobalAveragePool` + `Reshape` | 쉬움 | ONNX 는 `[N,C,1,1]`, 우리는 `[N,C]` |
| 8 | `Flatten` | `Flatten(axis=1)` | 쉬움 | 의미가 정확히 같다 |
| 9 | `Reshape { shape }` | `Reshape` | 쉬움 | shape 이니셜라이저 `[0, ...shape]`, 0 = 배치 차원 유지 |
| 10 | `Activation { act }` | §1.3 표 | 보통 | `Gelu`·`Silu` 만 전개가 필요 |
| 11 | `Dropout { p }` | **노드 없음** | 쉬움 | 추론 그래프에서 제거하고 엣지를 이어 붙인다 |
| 12 | `BatchNorm` | `BatchNormalization` | 쉬움 | running 통계를 우리가 이미 저장한다(§1.3) |
| 13 | `LayerNorm` | `LayerNormalization(axis=-1)` | 쉬움 | **opset 17** |
| 14 | `Add` | `Add` | 쉬움 | |
| 15 | `Mul` | `Mul` | 쉬움 | |
| 16 | `Concat { dim }` | `Concat(axis=dim+1)` | 쉬움 | 우리 `dim` 은 샘플 축이라 **+1 보정** |
| 17 | `Embedding { vocab, dim }` | `Cast(to=INT64)` + `Gather(axis=0)` | 쉬움 | 우리 인덱스는 f32 텐서라 Cast 가 필요 |
| 18 | `Lstm { .. }` | `LSTM` | **어려움** | 게이트 재배열 + 전치 + 레이아웃(§1.5) |
| 19 | `Gru { .. }` | `GRU` | **어려움** | 위 + `linear_before_reset=1` |
| 20 | `MultiHeadAttention { heads, dropout }` | 8개 노드로 분해 | 보통 | §1.4 |

**17종이 거의 그대로 대응하고, 진짜 일은 순환 레이어 둘뿐이다.**

### 1.3 활성화와 가중치 규약

활성화:

| `Act` | ONNX (opset 17) |
|---|---|
| `Relu` | `Relu` |
| `LeakyRelu { slope }` | `LeakyRelu(alpha = slope)` |
| `Gelu` | `Mul(X, Mul(0.5, Add(1, Erf(Div(X, √2)))))` — **정확형(erf)** |
| `Silu` | `Mul(X, Sigmoid(X))` |
| `Sigmoid` | `Sigmoid` |
| `Tanh` | `Tanh` |
| `Softmax` | `Softmax(axis=-1)` |
| `LogSoftmax` | `LogSoftmax(axis=-1)` |

`Gelu` 에 함정이 있다. burn 의 `activation::gelu` 는 `x·½(1+erf(x/√2))` 정확형이고 `gelu_approximate` 가 tanh 근사형이다.
우리는 정확형을 쓰므로 **tanh 근사로 내보내면 값이 달라진다**. opset 20 의 `Gelu` 연산자도 `approximate="none"` 이 기본이라
맞지만, 17 을 겨냥하므로 `Erf`(opset 9+)로 전개하는 쪽을 쓴다.

가중치(우리 safetensors 이름은 `"{node_id}.{part}"`):

| 우리 파라미터 | 우리 형상 | ONNX 이니셜라이저 | 변환 |
|---|---|---|---|
| `weight` (Linear) | `[in, out]` | `MatMul` 의 B `[in, out]` | **없음** |
| `bias` (Linear) | `[out]` | `Add` 의 두 번째 입력 | **없음** (브로드캐스트) |
| `weight` (Conv2d) | `[out, C, kh, kw]` | `Conv` 의 W `[M, C, kH, kW]` | **없음** |
| `gamma`/`beta` (BatchNorm) | `[C]` | `scale` / `B` | **없음** |
| `running_mean`/`running_var` | `[C]` | `input_mean` / `input_var` | **없음** |
| `gamma`/`beta` (LayerNorm) | `[N]` | `Scale` / `B` | **없음** |
| `q_weight` 등 (MHA) | `[D, D]` | `MatMul` 의 B | **없음** |
| `weight_ih` (LSTM/GRU) | `[D, gates·H]` | `W` `[dir, gates·H, D]` | **전치 + 게이트 재배열 + dir 축** |
| `weight_hh` | `[H, gates·H]` | `R` `[dir, gates·H, H]` | 같음 |
| `bias_ih` + `bias_hh` | 각 `[gates·H]` | `B` `[dir, 2·gates·H]` | 재배열 후 이어붙이기 |

**운 좋은 사실 하나.** burn 의 `module::linear` 이 `x @ w` 라 우리 `Linear.weight` 가 `[in, out]` 이다. PyTorch 는 `[out, in]`
이라 ONNX 로 내보낼 때 전치가 필요한데, **우리는 그 전치가 필요 없다.** `Conv2d` 도 형상이 그대로 맞는다. 순환 레이어를
빼면 가중치 변환 코드가 아예 없는 셈이다.

**BatchNorm 도 운이 좋다.** ONNX `BatchNormalization` 은 추론에서 `scale`·`B`·`input_mean`·`input_var` 네 개를 **전부 필수**로
요구하는데, 우리는 `running_mean`/`running_var` 를 학습 파라미터가 아닌 채로 이미 저장하고 있다(`exec.rs` 의 `init_params`).
별도 작업이 없다.

### 1.4 어텐션 분해 (opset 17)

`D = heads · head_dim` 일 때, 우리 `self_attention` 과 같은 순서로 8개 노드를 만든다.

```
Q = Add(MatMul(X, q_weight), q_bias)        # [B, L, D]
Qh = Transpose(Reshape(Q, [0, 0, heads, head_dim]), perm=[0,2,1,3])   # [B, heads, L, head_dim]
Kh, Vh 도 같은 방식
S  = Div(MatMul(Qh, Transpose(Kh, perm=[0,1,3,2])), √head_dim)        # [B, heads, L, L]
A  = Softmax(S, axis=-1)
C  = Reshape(Transpose(MatMul(A, Vh), perm=[0,2,1,3]), [0, 0, D])     # [B, L, D]
Y  = Add(MatMul(C, out_weight), out_bias)
```

`Reshape` 의 shape 이니셜라이저에 **0 을 쓰는 것이 핵심**이다. ONNX `Reshape` 는 `allowzero=0`(기본)에서 0 을 "그 자리의
입력 차원을 그대로"로 읽으므로, 배치와 길이가 심볼릭이어도 안전하다.

`dropout` 은 추론에서 항등이므로 내보내지 않는다.

### 1.5 순환 레이어 — 여기가 진짜 일이다

세 가지가 동시에 다르다.

**(가) 게이트 순서.** 우리 구현(`exec.rs` 의 `recurrent`)은 PyTorch 순서를 따른다.

| | 우리 / PyTorch | ONNX | 재배열 인덱스 |
|---|---|---|---|
| LSTM | `i, f, g, o` | `i, o, f, c` | `[0, 3, 1, 2]` |
| GRU | `r, z, n` | `z, r, h` | `[1, 0, 2]` |

`hidden` 크기 블록 단위로 축 0 을 재배열한다. LSTM 의 `g` 와 ONNX 의 `c` 는 같은 게이트다(이름만 다르다).

**(나) 전치.** 우리 `weight_ih` 는 `[D, 4H]`, ONNX `W` 는 `[1, 4H, D]` 다. 전치한 뒤 방향 축을 `unsqueeze` 한다.
편향은 우리가 `bias_ih`·`bias_hh` 를 따로 두는데 ONNX `B` 도 `[Wb, Rb]` 를 이어 붙인 `[dir, 8H]` 라 구조가 같다 —
각각 재배열한 뒤 이어 붙이면 된다.

**(다) 레이아웃.** 우리 텐서는 `[B, L, D]`(batch-first), ONNX LSTM 기본은 `layout=0` 즉 `[L, B, D]`(seq-first) 다.
두 길이 있다.

- `layout=1` 로 batch-first 를 선언한다. opset 14+ 이고 tract 도 `batch_first` 를 읽는다(`onnx/src/ops/rec/common.rs`).
  출력이 `[B, L, dir, H]` 라 우리 `[B, L, dir·H]` 로 맞추려면 `Reshape` 하나가 더 붙는다.
- **`layout=0` + 앞뒤로 `Transpose`.** 노드가 둘 늘지만 **모든 ONNX 런타임이 지원하는 안전한 길**이다.

**`layout=0` 을 권한다.** 내보내기의 목적이 이식성이고, `Transpose` 두 개는 비용이 아니다.

출력 정리:

| `return_sequence` | ONNX 출력 | 우리 형상으로 |
|---|---|---|
| `true` | `Y` `[L, dir, B, H]` | `Transpose(perm=[2,0,1,3])` → `Reshape([0,0,dir·H])` → `[B, L, dir·H]` |
| `false` | `Y_h` `[dir, B, H]` | `Transpose(perm=[1,0,2])` → `Reshape([0, dir·H])` → `[B, dir·H]` |

양방향 이어붙임 순서는 맞는다. 우리는 마지막 차원에 정방향｜역방향 순으로 `cat` 하고, ONNX `Y` 의 `dir` 축도 0 이 정방향
1 이 역방향이다.

**GRU 는 `linear_before_reset=1` 을 반드시 명시해야 한다.** ONNX 기본값은 0 인데, 우리 구현은
`n = tanh(gi_n + r ⊙ gh_n)` 이고 `gh_n` 이 `bias_hh` 를 포함하므로 `linear_before_reset != 0` 쪽이다. 이것을 빠뜨리면
**오류 없이 값만 틀린다** — 재검증 테스트가 반드시 잡아야 하는 항목이다.

### 1.6 protobuf 를 어떻게 쓸 것인가

세 후보를 비교했다.

| 방법 | 배포 바이너리 | 빌드 의존 | 위험 |
|---|---|---|---|
| **A. `onnx.proto3` 를 한 번 생성해 커밋** | `prost` + `prost-derive` (2 크레이트) | **없음** | 생성기를 개발 시점에 한 번 돌려야 한다 |
| B. `tract_onnx::pb` 재사용 | tract 전체 (**+34 MiB**) | 없음 | tract 가 "not stable surface" 라 `pb` 경로가 마이너 버전에서 바뀔 수 있다 |
| C. `onnx-pb` 0.1.4 | 작음 | 없음 | **2020년 아카이브. prost 0.6 / bytes 0.5 라 지금 생태계와 타입이 안 섞인다** |

**A 를 권한다.** tract 가 하는 방식과 똑같다 — 생성된 `.rs`(약 46 KB)를 `crates/nl-engine/src/onnx/pb.rs` 로 커밋하면
사용자 빌드에 `protoc` 도 코드 생성도 필요 없다.

`prost-build` 는 **0.11(2022-07)부터 `protoc` 바이너리를 요구한다**. 그래서 생성 단계는 순수 Rust 경로를 쓴다. 둘 중 하나다.

- `protobuf-codegen` 의 `.pure()` 모드 (rust-protobuf 3.x) — burn 팀의 `onnx-ir` 가 실제로 쓰는 검증된 방법
- `protox`(순수 Rust protobuf 컴파일러) 로 `FileDescriptorSet` 을 만들어 `prost_build::Config::compile_fds()` 에 넘기기

어느 쪽이든 **개발자가 한 번 돌리고 결과를 커밋**하므로 사용자에게는 차이가 없다. `bytes` 는 이미 우리 의존성 트리에 있다.

### 1.7 검증 — tract 왕복

```
우리 그래프 + safetensors
  → export() → model.onnx
  → tract_onnx::onnx().model_for_path() → with_input_fact() → into_optimized() → into_runnable()
  → run(같은 입력)
  → nl_engine::Session::run(같은 입력) 과 비교 (허용 오차 1e-4 정도)
```

**`tract-onnx` 를 `[dev-dependencies]` 로만 넣으면 배포 바이너리는 전혀 커지지 않는다.** 내보내기만 할 거라면 이게
결정적인 이점이다.

테스트에 반드시 넣어야 할 것:

1. MLP · CNN(Conv/BN/Pool/Flatten) — 배관 검증
2. **GRU** — `linear_before_reset` 을 빠뜨리면 오류 없이 값만 틀리는 유일한 항목
3. **양방향 LSTM, `return_sequence` 양쪽** — 게이트 재배열과 레이아웃이 한꺼번에 걸린다
4. 어텐션 블록 — 분해가 맞는지
5. 배치 크기를 바꿔 두 번 (심볼릭 배치가 실제로 도는지)

## 2. 가져오기 — tract 로 추론 전용

### 2.1 API 흐름 (0.23.7 에서 확인)

```rust
let model = tract_onnx::onnx().model_for_path(path)?;
let b = model.sym("B");                                  // 동적 배치
let model = model
    .with_input_fact(0, f32::fact(dims!(b, 3, 224, 224)).into())?
    .into_optimized()?
    .into_runnable()?;                                   // IntoRunnable 트레이트
let out = model.run(tvec!(input.into()))?;
```

`into_runnable` 은 0.23.7 에서 인허런트 메서드가 아니라 `IntoRunnable` 트레이트 메서드다 — `use tract_onnx::prelude::*`
가 필요하다.

**심볼릭 차원이 완전히 지원된다.** ONNX 의 `dim_param`(예: `"batch_size"`)을 같은 이름의 심볼로 읽고, 실행 시 실제 입력
형상으로 해석한다. 동적 배치·가변 시퀀스가 그대로 산다.

**주의 하나.** tract README 가 이제 `tract` 파사드 크레이트를 "the authoritative public API" 로 선언하고 `tract-onnx` 같은
내부 크레이트는 "not stable surface" 라고 적었다. 가져오기만 할 거라면 파사드 쪽이 장기적으로 안전하다. 다만 §1.6 의 B안
(`pb` 타입 재사용)을 택하면 `tract-onnx` 를 직접 써야 한다 — 이것도 A안을 권하는 이유 중 하나다.

### 2.2 지원 범위

tract 가 우리 20종에 대응하는 연산자를 전부 읽는다. `onnx/src/ops/` 의 레지스트리에 `Conv`, `BatchNormalization`,
`LayerNormalization`, `MaxPool`, `AveragePool`, `Softmax`, `LogSoftmax`, `Gelu`, `LSTM`, `GRU`, `RNN`, `Scan`, `Gather`,
`Attention`, `MultiHeadAttention` 등이 등록되어 있다. 바깥에서 받은 모델도 흔한 CNN/RNN 계열은 대체로 돈다.

연산자 목록 문서는 **없다**. 소스의 `register_all_ops` 가 사실상의 목록이다. 그래서 "어떤 모델이 되는지" 를 사전에
장담할 수 없고, **불러오기 실패를 정상 경로로 다뤄야 한다** — 사용자에게 "이 모델의 `<연산자>` 는 지원되지 않습니다" 를
보여 주는 UI 가 필요하다.

### 2.3 파이프라인 노드 설계안

지금 `PNodeKind::Model { model: ModelId, payload: Option<PayloadId> }` 가 우리 모델만 가리킨다. 추가 전용으로 한 변형을
더한다.

```rust
pub enum PNodeKind {
    // …기존…
    /// 바깥에서 받은 ONNX 모델. 추론 전용이라 학습·가중치 편집 대상이 아니다.
    OnnxModel {
        /// `base_dir` 아래 상대 경로 (파일 소스·가중치와 같은 규칙).
        path: String,
        #[serde(default)]
        payload: Option<PayloadId>,
    },
}
```

설계상 짚을 것 넷.

- **경로는 `base_dir` 아래로 제한한다.** 기존 파일 소스·가중치 경로와 같은 규칙이다(보안 리뷰 원칙).
- **`payload` 로 인코딩·디코딩을 붙인다.** 우리 `PayloadSpec` 이 그대로 쓰인다. ONNX 쪽 입출력 이름은 `payload.inputs`/
  `outputs` 순서에 대응시킨다 — 우리 `decode_outputs`/`encode_inputs` 규약과 같은 모양이다.
- **모델 크기 상한이 필요하다.** `limits.rs` 의 `MAX_WEIGHTS_BYTES` 같은 방어선을 ONNX 파일에도 건다. protobuf 는
  중첩 깊이 공격이 가능한 포맷이다.
- **`ModelDef` 로 만들지 않는다.** 가져온 ONNX 는 캔버스에 그려지지 않고 노드 하나로 남는다. "추론 전용" 이 그 뜻이다.
  ONNX → 우리 `LayerKind` 역변환은 사실상 별개의 큰 일이고, 이번 범위가 아니다.

### 2.4 바이너리 크기 — **+34 MiB**

`tract-onnx = "0.23"` 하나만 의존하는 최소 프로그램과 같은 골격의 빈 프로그램을 각각 빌드해 쟀다.

| 프로필 | 빈 프로그램 | tract-onnx 포함 | 증가분 |
|---|---|---|---|
| **저장소 릴리스 프로필** (`opt-level=3`, `lto="thin"`, strip 없음) | 2.14 MiB | **36.1 MiB** | **+34.0 MiB** |
| 공격적 프로필 (`lto=true`, `codegen-units=1`, strip, `panic=abort`) | 0.30 MiB | 20.7 MiB | +20.4 MiB |

**+34.0 MiB 가 지금 우리에게 해당하는 값이다.** 저장소 어디에도 `strip` 설정이 없어 배포 바이너리가 미스트립으로 나간다.
현재 `nl-runtime` 릴리스 바이너리가 **74.2 MiB** 이므로 **약 +46%** 다. `strip` 을 켜면 20 MiB 대로 내려가지만, 그건 tract 와
무관하게 지금도 할 수 있는 별개의 절감이다.

의존 크레이트는 `cargo tree` 로 세었다.

| 항목 | 수 |
|---|---|
| `tract-onnx` 의 전체 의존 크레이트 | 112 |
| `nl-runtime` 의 현재 의존 크레이트 | 456 |
| **tract 가 새로 끌어오는 것** | **35** |

새로 들어오는 35개 중 11개가 tract 자신(`tract-core`, `tract-linalg`, `tract-data`, `tract-hir`, `tract-nnef`,
`tract-extra`, `tract-onnx-opl`, `tract-pulse`, `tract-pulse-opl`, `tract-transformers`)이고, 나머지는 `prost`,
`rustfft`, `minijinja`, `string-interner`, `erased-serde`, `inventory` 등이다.

**기능 플래그로 줄일 수 없다.** `tract-onnx` 0.23.7 의 `Cargo.toml` 에는 `optional` 의존성이 하나도 없고 기능도
`getrandom-js` 뿐이다. `tract-extra`·`tract-transformers`·`tract-pulse` 가 전부 필수 의존이다. 깎을 수 없는 값이다.

### 2.5 Windows 크로스 컴파일 — **된다 (실측)**

우려했던 지점이 있었다. `tract-linalg` 의 `build.rs` 가 x86_64 MSVC 타깃에서 어셈블리를 컴파일하는데, `cargo-xwin` 이
제공하는 것은 MSVC 헤더·라이브러리와 `lld-link` 이고 MASM 어셈블러(`ml64.exe`)는 들어 있지 않다.

**실제로 해 보니 문제없이 빌드된다.**

```
cargo xwin build --release --target x86_64-pc-windows-msvc
    Finished `release` profile [optimized] target(s) in 14m 09s
```

| 항목 | 결과 |
|---|---|
| 산출물 | `onnxprobe.exe` — `PE32+ executable for MS Windows 6.00 (console), x86-64` |
| 크기 | 18.8 MiB (공격적 프로필 기준) |
| 빌드 시간 | 14분 09초 (부하 20인 공용 머신) |
| 어셈블리 커널 | **컴파일됨** — `tract-linalg` 출력에 `avx512vnni_mmm_i32_16x16`, `tanh_f32`, `silu_f32` 등 `.o` 와 `x86_64_avx512vnni.lib` 가 생성됐다 |

즉 `cc` 크레이트가 `cargo-xwin` 의 clang-cl 계열 툴체인으로 어셈블리를 처리한다. **관리자 권한도 Visual Studio 설치도
필요 없다** — 지금 우리 Windows 런타임 빌드 방식이 그대로 통한다.

## 3. 권장 순서와 공수

### 3.1 순서

| 단계 | 내용 | 배포 바이너리 영향 | 추정 |
|---|---|---|---|
| **1** | **MLP/CNN 내보내기 + tract 왕복 검증** | **0** (tract 는 dev-dep) | 2~3일 |
| 2 | `LayerNorm`·`Embedding`·`Concat`·`Reshape`·`GlobalAvgPool` 내보내기 | 0 | 0.5일 |
| 3 | LSTM/GRU 내보내기 (게이트 재배열·레이아웃·`linear_before_reset`) | 0 | 1.5~2일 |
| 4 | 어텐션 분해 내보내기 | 0 | 1일 |
| 5 | 앱 UI: "ONNX 로 내보내기" 메뉴 + 미지원 항목 경고 | 0 | 0.5일 |
| 6 | 가져오기: `PNodeKind::OnnxModel` + tract 런타임 | **+34 MiB** | 2일 |

**합계 대략 8~10일.** 1~5 만 하면 6~7일이고 바이너리는 그대로다.

### 3.2 왜 MLP/CNN 내보내기가 첫 조각인가

세 가지가 한꺼번에 맞아떨어진다.

- **위험한 부분을 먼저 친다.** 새로 배워야 하는 건 연산자 수식이 아니라 **protobuf `ModelProto` 배관**이다
  (이니셜라이저, `ValueInfoProto`, `opset_import`, 심볼릭 차원, 토폴로지 순서). MLP/CNN 은 그 배관을 가장 단순한
  연산자로 전부 훑는다.
- **첫날부터 객관적인 합격 판정이 생긴다.** tract 왕복 비교는 사람이 눈으로 보는 검증이 아니라 숫자 비교다. 이 뼈대가
  있으면 이후 LSTM·어텐션은 "테스트를 통과시키는" 작업으로 바뀐다.
- **바이너리를 늘리지 않고 가치를 낸다.** 사용자가 학습한 모델을 다른 도구로 가져갈 수 있게 되는데, 배포 크기는 그대로다.

### 3.3 결정이 필요한 것

1. **가져오기가 +34 MiB(+46%) 값어치를 하는가.** 내보내기는 공짜지만 가져오기는 아니다. 로드맵이 "가져오기(추론 전용)/
   내보내기(검토)" 순으로 적혀 있는데, **조사 결과는 반대 순서를 가리킨다.**
2. **protobuf 경로.** §1.6 의 A(생성 후 커밋)를 권하지만, 가져오기를 먼저 한다면 B(`tract_onnx::pb` 재사용)로 코드를
   덜 쓸 수 있다. 다만 tract 가 그 표면을 안정 API 로 보장하지 않는다.
3. **`tract` 파사드 vs `tract-onnx` 직접.** 가져오기를 할 때 정해야 한다.

### 3.4 조사하다 남은 것

- tract 가 `com.microsoft` 도메인 contrib 연산자를 **op_type 이름만으로** 디스패치한다. 표준 `Attention` 핸들러가
  MS contrib 의 패킹된 QKV 입력을 제대로 처리하는지는 확인하지 않았다. 바깥 모델을 받을 때 문제가 될 수 있다.
- ONNX 모델의 `FunctionProto`(로컬 함수) 지원 여부 — 확인하지 않았다.

## 4. 측정 방법 (재현용)

크기·의존성 수치는 스크래치 크레이트 두 개를 만들어 실측했다. `tract-onnx = "0.23"` 하나만 의존하는 프로그램과,
같은 골격에 의존성이 없는 프로그램이다.

```rust
// tract 쪽 main.rs — 로딩·최적화·실행 경로를 전부 링크에 남기기 위한 최소 코드
use tract_onnx::prelude::*;
fn main() -> TractResult<()> {
    let path = std::env::args().nth(1).unwrap_or_default();
    let model = tract_onnx::onnx().model_for_path(&path)?.into_optimized()?.into_runnable()?;
    let input: Tensor = tract_ndarray::Array2::<f32>::zeros((1, 4)).into();
    println!("{:?}", model.run(tvec!(input.into()))?[0].shape());
    Ok(())
}
```

- 크기: `cargo build --release` 후 바이너리 바이트 수. 저장소 릴리스 프로필(`opt-level=3`, `lto="thin"`, strip 없음)과
  공격적 프로필 두 벌을 각각 쟀다.
- 의존성: `cargo tree --edges normal --prefix none` 결과를 크레이트 이름으로 중복 제거해 세고, `nl-runtime` 의 같은 목록과
  `comm -13` 으로 차집합을 냈다.
- Windows: `cargo xwin build --release --target x86_64-pc-windows-msvc`, 산출물은 `file` 로 확인.
- 머신 부하가 20~50 사이로 흔들려 **빌드 시간은 참고치일 뿐**이다. 크기와 의존성 수는 부하와 무관하다.
